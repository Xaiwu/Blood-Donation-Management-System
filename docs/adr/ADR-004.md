# ADR-004: Resiliencia, modos de falla y dependencias

* **Estado:** Aceptado
---

## Contexto 

Al crear solicitudes o intentar revertirlas, esto depende directamente de que el
sistema de reservas responda correctamente, por lo que es necesario establecer un protocolo
claro para manejar los fallos o alta latencia.

---

## Alternativas consideradas
### Opción A — Aplicación monolítica

Sin timeout en la comunicación.

### Opción B — Separación en dos servicio

Timeout corto

## Decisión

Se decidió implementar un timeout corto devolviendo error de servicio no dispo-
nible en caso de que se sobrepase el tiempo.

## Justificación

Se decidió mantener la máxima consistencia en la API REST para que los
clientes(hospitales), cuenten siempre con toda la información, en este caso si es que el servicio
este caido o no (error 503), con el propósito de que no generen desiciones importantes en
base a potenciales errores.

## Costo aceptado

Se acepta fallar a proposito solicitudes que podrian haber sido resueltas
en un tiempo un poco mayor al timeout.

## Consecuencias

* Principalmente para los hospitales implica traspasarles la responsabilidad de reintentar la petición.
* Se debe estudiar bien un timeout óptimo que sea razonable y no cause mucha sobrecarga en el sistema.
* El dia de mañana si por ejemplo los hospitales piden que este proceso sea automático, se debe considerar como se menciono antes cambiar a una arquitectura asincronica como Apache Kafka.
