# ADR-001: Estilo de integración y descomposición

* **Estado:** Aceptado
---

## Contexto 

El sistema de gestión de donación de sangre integra dos responsabilidades principales: la gestión de las solicitudes realizadas por los hospitales y la gestión de las unidades de sangre disponibles. El sistema de Solicitudes requiere consultar y modificar la disponibilidad de unidades antes de registrar o revertir una solicitud.

El problema de integración se origina porque estas responsabilidades pertenecen a sistemas que deben mantener información diferenciada. El sistema de Reservas mantiene la información sobre los tipos de sangre y las unidades disponibles, mientras que el sistema de Solicitudes gestiona los hospitales, solicitantes y las solicitudes de unidades. Reservas es propietario del inventario y Solicitudes es propietario del proceso de solicitud.

A partir de esto, se debe decidir cómo dividir las responsabilidades del sistema y dónde establecer la frontera entre ellas.

## Alternativas consideradas
### Opción A — Aplicación monolítica

Implementar hospitales, solicitudes e inventario de sangre dentro de una única aplicación y una única base de datos.

### Opción B — Separación en dos servicios

Separar el sistema en un servicio de Solicitudes y un servicio de Reservas. El primero sería responsable de hospitales y solicitudes, mientras que el segundo sería responsable del inventario y de las operaciones de reserva y liberación de unidades.

La comunicación entre ambos servicios se realizaría mediante una interfaz gRPC. Cada servicio mantendría su propio almacenamiento.

## Decisión
Se decidió implementar el sistema como dos servicios independientes: solicitudes-service y reservas-service.

El servicio solicitudes-service será responsable de gestionar los hospitales solicitantes y las solicitudes de unidades de sangre. El servicio reservas-service será responsable de mantener el inventario y ejecutar las operaciones de consulta, reserva y liberación de unidades.

La frontera entre ambos servicios se establece según la responsabilidad sobre los datos: Reservas es el propietario de la información relacionada con la disponibilidad de unidades de sangre, mientras que Solicitudes es responsable del proceso de solicitud realizado por los hospitales.

La comunicación entre ambos se realizará mediante gRPC, de modo que Solicitudes solicite a Reservas las operaciones relacionadas con el inventario sin acceder directamente a su base de datos.

## Justificación
La separación permite mantener una única responsabilidad sobre el inventario de sangre. De esta manera, reservas-service mantiene la información de las unidades disponibles y controla las operaciones que modifican dicho inventario, mientras que solicitudes-service no necesita conocer la estructura interna de almacenamiento de Reservas.

Esta frontera también permite aplicar la separación de bases de datos por servicio. Cada servicio mantiene su propio almacenamiento y la comunicación se realiza mediante un contrato explícito, en lugar de compartir directamente una base de datos.

Frente a un monolito, esta alternativa introduce mayor complejidad, pero proporciona una separación más clara entre el proceso de gestión de solicitudes y la administración del inventario. Además, permite que la integración entre ambas responsabilidades sea explícita y pueda evolucionar mediante un contrato gRPC.
## Costo aceptado
La principal consecuencia aceptada es el aumento de complejidad debido a la comunicación. Una solicitud puede depender de que reservas-service esté disponible y responda correctamente.

Además, una operación que involucra ambos servicios puede requerir mecanismos de compensación cuando una parte de la operación se completa y otra falla. Por ejemplo, al registrar una solicitud se debe reservar primero la cantidad correspondiente de unidades y posteriormente registrar la solicitud. Si el registro de la solicitud falla, es necesario liberar las unidades reservadas.

Por lo tanto, se acepta una mayor complejidad de coordinación a cambio de mantener separadas las responsabilidades y la propiedad de los datos.

## Consecuencias

* solicitudes-service será responsable de hospitales y solicitudes.
* reservas-service será responsable del inventario y de las operaciones de reserva y liberación.
* Cada servicio tendrá su propio almacenamiento.
* Solicitudes no accederá directamente a la base de datos de Reservas.
* La comunicación entre ambos servicios se realizará mediante gRPC.
* Una falla o indisponibilidad de Reservas puede afectar las operaciones de Solicitudes que requieren consultar o modificar el inventario.
* Las operaciones que involucran ambos servicios requieren considerar consistencia y compensación ante fallas.
