# ADR-003: Contrato, versionado y evolución

* **Estado:** Aceptado

## Contexto 
El sistema está compuesto por dos servicios independientes: Solicitudes y Reservas, los cuales necesitan comunicarse mediante contratos  definidos.

El servicio Solicitudes expone una API REST para los clientes externos, mientras que Reservas ofrece un servicio gRPC utilizado internamente por Solicitudes. Debido a esta separación, ambos servicios necesitan conocer de manera explícita qué operaciones están disponibles, qué datos deben enviar y qué respuestas pueden recibir.

Además, los contratos deben poder evolucionar sin generar cambios incompatibles entre los servicios. Esto es importante porque una modificación en los datos de una solicitud o en las operaciones de reserva podría afectar al otro servicio.

Por esta razón, se requiere mantener los contratos separados del código de implementación y versionarlos dentro del repositorio.

## Alternativas consideradas
### Opción A — Contratos definidos principalmente en el código
Las operaciones y estructuras de datos se definirían directamente mediante los modelos y funciones de cada servicio, sin mantener una especificación formal independiente.

### Opción B — Contratos explícitos mediante OpenAPI y Protobuf
Mantener un contrato OpenAPI para la API REST de Solicitudes y un archivo .proto para el servicio gRPC de Reservas, ambos almacenados y versionados junto con el código fuente.


## Decisión
Se decidió utilizar contratos explícitos y versionados, manteniendo:
* openapi.yaml para definir la API REST pública de Solicitudes.
* reservas.proto para definir el servicio gRPC interno de Reservas.
* La API REST bajo la versión /v1.

Cuando un cambio es incompatible con el contrato público, se deberá considerar una nueva versión de la interfaz. Pero, si el cambio es compatible, se puede mantener la misma versión.

## Justificación

Esta decisión permite separar claramente el contrato de comunicación de la implementación interna de cada servicio.

En REST, OpenAPI permite documentar los endpoints disponibles, sus parámetros, estructuras de datos y respuestas. Esto facilita que un cliente conozca cómo utilizar el servicio sin depender de su implementación interna.

En gRPC, el archivo .proto define explícitamente los mensajes y operaciones disponibles entre Solicitudes y Reservas. A partir de este contrato se generan las estructuras necesarias para la comunicación, reduciendo la posibilidad de que ambos servicios interpreten de forma diferente los datos intercambiados.

El versionado mediante /v1 también permite establecer una interfaz estable para los consumidores de la API. De esta forma, los cambios internos de implementación no requieren modificar necesariamente el contrato mientras se mantenga la compatibilidad.

## Costo aceptado

El principal costo es que los contratos deben mantenerse sincronizados con la implementación. Un cambio en una operación REST o gRPC puede requerir modificar la especificación, actualizar el código correspondiente y verificar nuevamente la comunicación entre servicios.

También se acepta la necesidad de mantener una estrategia de versionado cuando en el futuro aparezcan cambios incompatibles.

## Consecuencias
Como consecuencia de esta decisión:
* La API REST queda documentada mediante OpenAPI y expuesta bajo /v1.
* La comunicación interna queda definida mediante Protobuf.
* Los contratos son visibles y revisables dentro del repositorio.
* Los servicios pueden evolucionar internamente sin modificar necesariamente sus interfaces.
* Los cambios incompatibles requieren una estrategia explícita de versionado.
* Se agrega el costo de mantener actualizados los archivos openapi.yaml y reservas.proto.
