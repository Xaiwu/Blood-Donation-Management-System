# ADR-002: Selección de REST frente a gRPC

* **Estado:** Aceptado
---

## Contexto 

Se tenia que decidir que tecnologías usar para los sistemas de reserva que maneja
el stock de sangre, y el sistema de solicitudes que gestiona los hospitales y solicitudes de
estos, para este último esta planificado que se use en un futuro para una plataforma web,
por ultimo sobre el sistema de reserva hay que hacerlo apto para que soporte una gran
cantidad de consultas sobre el stock de la sangre.

---

## Alternativas consideradas
### Opción A — Todo con API REST: 

Todo con API REST: Ofrece una sencilla implementación, legibilidad y
flexibilidad en las estructuras de datos pero a cambio es mucho menos eficiente debido
a la latencia y tamaño del los mensajes JSON

### Opción B — Todo con gRPC:

Tiene un alto rendimiento y un tipado estricto ideal para
alto volumen de consultas, pero resulta incompatible si se usa directamente para una
web, teniendo que pasar por adaptadores que aumentan la complejidad y legibilidad
del código

### Opción C - Sistema mixto con REST y gRPC: 

Sistema mixto con REST y gRPC: Se obtienen los beneficios de ambas
opciones anteriores con el único contra que se deben mantener 2 arquitecturas con
protocolos distintos.

## Decisión

Se elige la opción C, la parte pública se manejar+a con REST y la comunicación
interna con gRPC

## Justificación

Esta opción máximiza la interoprabilidad para la cara pública (REST) y
máximiza el rendimiento, para el ámbito interno, usar REST (mensajes JSON) tiene un coste
en tamaño de 2 hasta 9 veces y un tiempo de serialización/deserialización, unas 20 veces más
siendo exponencial (desde unas 17 a 27 veces mayor) al tamaño del stock. Esto demostrado
en la sección del experimento 2 y los anexos de tiempo en el informe

## Costo aceptado

Se acepta la pérdida de tener que mantener 2 arquitecturas distintas,
aumentando la complejidad del sistema completo.

## Consecuencias

* Implica que es de vital importancia trabajar en que la comunicación entre
la API y el gRPC, para mantener consistencia entre las bases de datos.
* A medida quecambie el contexto por ejemplo aumentando la cantidad de microservicios, el sistema se
vuelve vulnerable cada vez más a los timeouts, por lo que seria necesario ver un cambio de
arquitectura a un sistema asincronico como Apache Kafka.
