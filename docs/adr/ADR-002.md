# ADR-002: Selección de REST frente a gRPC

* **Estado:** Aceptado (revisado tras el Experimento 2)
---

## Contexto 

Se tenía que decidir qué tecnologías usar para el sistema de Reservas, que maneja el stock de sangre, y para el sistema de Solicitudes, que gestiona los hospitales y sus solicitudes. Solicitudes está planificado para que en el futuro lo use una plataforma web. Reservas es un servicio interno: solo lo llama Solicitudes, y cada llamada debe tener un tiempo máximo de espera, porque una dependencia lenta no puede bloquear la API pública.

---

## Alternativas consideradas
### Opción A — Todo con API REST

Implementación sencilla, legible y flexible, y la misma tecnología en ambos lados. Pero la interfaz interna quedaría sin un contrato tipado que compile: cada servicio interpretaría el JSON a su manera, y los tiempos máximos de espera habría que programarlos a mano en cada llamada.

### Opción B — Todo con gRPC

Contrato tipado y generación de código, pero un navegador no puede llamar gRPC directamente. La futura plataforma web necesitaría un proxy (gRPC-Web o un gateway), lo que agrega una pieza más y hace la API pública menos accesible para los hospitales.

### Opción C — Sistema mixto: REST hacia afuera y gRPC hacia adentro

Cada interfaz usa la tecnología adecuada para su consumidor. El costo es mantener dos protocolos.

## Decisión

Se elige la **Opción C**: la parte pública se expone con REST (`/v1`, OpenAPI) y la comunicación interna entre Solicitudes y Reservas usa gRPC (`reservas.proto`).

## Justificación

* **Hacia afuera, REST:** los hospitales y la futura web lo consumen con cualquier cliente HTTP, sin herramientas especiales, y se documenta con Swagger.
* **Hacia adentro, gRPC**, por tres razones que importan en este sistema:
  1. **Contrato tipado y versionado.** `reservas.proto` define los mensajes y el enum `TipoSangre`. Un tipo de sangre o un campo mal escrito es un error al generar el código, no al ejecutar (ver ADR-003).
  2. **Código generado.** Ambos Dockerfiles generan los stubs de cliente y servidor desde el mismo `.proto`, así que los dos servicios no pueden interpretar un mensaje distinto. El cliente .NET (`cliente-dotnet`) se generó del mismo archivo.
  3. **Deadlines nativos.** Cada llamada lleva `timeout=RESERVAS_TIMEOUT_S`, y gRPC la corta con `DEADLINE_EXCEEDED`. Este es el mecanismo que se midió en el Experimento 1 y que mantiene acotada la latencia de la API cuando Reservas está lento (ADR-004).

**El tamaño del mensaje no es la razón.** El Experimento 2 muestra que JSON pesa entre 2,3 y 9,1 veces más que Protobuf. En los listados esa razón es **constante (~8,3×)**, así que el costo crece de forma **lineal** con el tamaño, no exponencial. Serializar JSON tarda entre 16 y 31 veces más, pero en valores absolutos son microsegundos: los mensajes de este sistema pesan entre 42 y 130 bytes. Según el Experimento 1, la latencia está dominada por la cola en Reservas, del orden de segundos, unas 10⁶ veces más que la serialización. La eficiencia de Protobuf es real, pero con esta carga no cambia el rendimiento.

## Costo aceptado

Se acepta mantener dos protocolos y dos contratos (`openapi.yaml` y `reservas.proto`), lo que aumenta la complejidad del sistema y obliga a traducir los códigos de error gRPC a HTTP (`FAILED_PRECONDITION` → 409, `DEADLINE_EXCEEDED`/`UNAVAILABLE` → 503).

## Consecuencias

* La consistencia entre ambas bases depende de cómo se maneje la falla de la llamada gRPC. Esto se resuelve en ADR-004, con compensación y reconciliación.
* El tamaño del mensaje pasaría a ser relevante con listados grandes y frecuentes, o con enlaces de red limitados. Hoy el listado tiene solo 8 tipos de sangre.
* Si el contexto cambia, por ejemplo con más microservicios encadenados, aumenta la exposición a los timeouts y convendría evaluar una arquitectura asíncrona (por ejemplo, Apache Kafka).
