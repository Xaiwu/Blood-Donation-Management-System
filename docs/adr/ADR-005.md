# ADR-005: Autenticación de la API REST

* **Estado:** Aceptado
---

## Contexto

La API REST de Solicitudes es la única puerta de entrada al sistema y permite registrar y revertir solicitudes, es decir, reservar y liberar sangre. La usan los operadores del banco de sangre y los hospitales, y está planificado que la consuma una plataforma web.

Hay dos tipos de usuario con permisos distintos:

* **Lectura:** consulta hospitales, solicitudes y stock.
* **Escritura:** además registra hospitales y solicitudes, y las revierte.

Un error de permisos aquí no es menor: una reserva indebida bloquea unidades que otro hospital podría necesitar. Hay que decidir cómo se identifica quien llama y cómo se comprueba su rol.

## Alternativas consideradas

### Opción A — HTTP Basic

El cliente envía usuario y clave en cada petición.

* **A favor:** es lo más simple y está en todos los clientes HTTP.
* **En contra:** la clave viaja en **cada** petición, y cada petición la vuelve a comparar. Una web tendría que guardar la clave del usuario en el navegador para no pedirla siempre. Tampoco hay expiración: una credencial filtrada sirve hasta que alguien cambie la clave.

### Opción B — API Key

Cada cliente recibe una clave fija que envía en un encabezado.

* **A favor:** es simple para integraciones entre sistemas.
* **En contra:** identifica a una **aplicación**, no a una **persona**, así que no sirve para el personal del banco con roles distintos. Normalmente no expira, y para revocarla o rotarla hay que coordinar con cada cliente. El rol habría que buscarlo en una tabla en cada petición.

### Opción C — Token Bearer JWT (HS256) emitido por la propia API

El usuario se autentica una vez en `POST /v1/auth/token` y recibe un token firmado que incluye su rol (`rol`) y su expiración (`exp`).

* **A favor:** la clave viaja una sola vez. El token expira solo (`JWT_EXPIRA_SEGUNDOS`, 1 hora por defecto). El rol va dentro del token firmado, así que no se consulta ninguna base en cada petición. Es el mecanismo estándar para una web (encabezado `Authorization: Bearer`).
* **En contra:** un token emitido no se puede revocar antes de que expire, y el secreto HS256 debe protegerse.

### Opción D — OAuth2 / OpenID Connect con un proveedor de identidad externo

* **A favor:** es la opción más completa: revocación, inicio de sesión único y gestión de usuarios.
* **En contra:** exige desplegar y operar un servidor de identidad, lo que es desproporcionado para dos roles y un solo servicio público.

## Decisión

Se elige la **Opción C**: tokens Bearer JWT firmados con HS256, con los roles `lectura` y `escritura`.

* Los endpoints GET exigen un token válido (`verificar_token`). Sin token, con un token inválido o con uno expirado, responden **401** con `WWW-Authenticate: Bearer`.
* Los endpoints POST exigen además el rol `escritura` (`requiere_escritura`). Un token de lectura recibe **403 `PROHIBIDO`**.
* El secreto y las credenciales vienen de variables de entorno, no del código. Las claves se comparan en tiempo constante (`hmac.compare_digest`).
* El esquema está declarado en `contracts/openapi.yaml` (`bearerAuth`).

## Justificación

* **Separa autenticación de autorización:** 401 cuando no sabemos quién es, y 403 cuando sabemos quién es pero no tiene permiso. Con una API Key no habría un rol por persona.
* **Encaja con la futura plataforma web:** el navegador guarda un token que caduca, no la clave del operador.
* **No agrega dependencias en cada petición:** validar el token es una verificación de firma local. Si la API tuviera que consultar una base de sesiones en cada llamada, esa base sería un punto de falla más (ver ADR-004).
* **Limita el daño de una filtración:** un token robado deja de servir en una hora. Una clave Basic o una API Key filtrada sirven indefinidamente.
* **Es proporcional al problema:** OAuth2 resolvería necesidades que hoy no existen (muchos usuarios, inicio de sesión único) a cambio de operar otro servidor.

## Costo aceptado

* **No hay revocación inmediata:** si un token se filtra, vale hasta su `exp`. Se mitiga con la expiración de 1 hora.
* **Todas las instancias comparten un secreto HS256:** si `JWT_SECRET` no se define, se genera uno aleatorio y los tokens se invalidan al reiniciar.
* **Los usuarios son fijos**, dos y definidos por variables de entorno. No hay registro ni cambio de clave.
* **No hay límite de intentos** en `POST /v1/auth/token`.

## Consecuencias

* Para muchos usuarios, o para la integración con el sistema de identidad del hospital, la evolución natural es pasar a OAuth2/OIDC (Opción D). Los endpoints no cambian, porque siguen recibiendo un token Bearer con un rol.
* Antes de exponer la API fuera de una red controlada hay que agregar HTTPS (el token viaja en claro sobre HTTP) y un límite de intentos en el login.
* La comunicación interna gRPC con Reservas no lleva autenticación ni TLS. Se apoya en que Reservas solo es accesible desde la red de Docker y desde `127.0.0.1` del propio equipo (publicado así para el cliente .NET de prueba). En un despliegue real ese puerto no debe publicarse, o debe protegerse con mTLS.
